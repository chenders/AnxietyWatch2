# `0x2A35` fixtures — A&D UA-651BLE

Captured live 2026-08-03 from `00:09:1F:XX:XX:XX`. See
`docs/research/2026-08-03-ua651ble-ble-capture.md`.

These exist because the T-D2 brief shipped with a test vector derived by reading the spec rather
than by capturing hardware, and the derived value was wrong (`0xF14A → 7.4`; it is 33.0). A fixture
whose provenance is "the hardware produced it" cannot have that failure mode.

## Real frames

All `flags = 0x14` (mmHg, no timestamp, pulse present, no user id, status present), 11 bytes.

Every SFLOAT in this capture has exponent 0. **The exponent path is unexercised by real data** and
needs the synthetic cases below.

## Required synthetic cases

The hardware may never emit these, so they cannot be captured — but the decoder must handle them,
and radio input is attacker-controlled.

| Case | Purpose |
|---|---|
| `flags = 0x00`, 7 bytes | Minimum legal frame: no optional fields at all |
| `flags = 0x01` | kPa units — must convert (`× 7.50062`) at the decode boundary so the store only ever holds mmHg |
| `flags = 0x1E` | All optional fields present: **19 bytes** — 1 flags + 6 (three SFLOATs) + 7 timestamp + 2 pulse + 1 user id + 2 status. An earlier draft of this row said 20. Add the fields up before writing the buffer; a decoder built to require 20 rejects every legitimate fully-populated frame |
| Systolic mantissa `0x07FF` | SFLOAT NaN — `systolic` is `None`. Absence is representable; there is no "untouched" value to inspect |
| Negative exponent, u16 | `0xF04A` → 7.4 (exponent −1, mantissa 74). The capture is all exponent 0, so this path has no hardware coverage — and it is the path that produced this project's only known-wrong test vector |
| Negative exponent, full frame | `014af03cf042f0` → flags `0x01` (kPa), 7.4 / 6.0 / 6.6 kPa → **55.5 / 45.0 / 49.5 mmHg** after conversion at the decode boundary. **Little-endian on the wire**: `0xF04A` transmits as `4a f0`, so a frame written `01f04a…` decodes `0x4AF0` = exponent 4, mantissa 2800 → 2.8e7. An earlier draft of this row had exactly that byte order, in the file whose stated purpose is preventing hand-derived wrong vectors |
| Status `0x0004` | Irregular pulse detected |
| Truncation at every length 0..19 | Must return `None`, and must not read past the slice. **This governs the Rust decoder.** `tools/bp_capture.py` deliberately returns partial results instead — it is an operator-facing capture tool for a measurement the cuff has already deleted, so showing three good vitals beats showing none. The two behaviours are intentional and must not be reconciled by changing the Rust side |
| `flags = 0x02` with 8 bytes | Timestamp flag set but payload too short — the truncation check that matters most |

## Note on provenance

The four real frames are actual measurements. They are kept verbatim because the byte layout is
what the tests exercise and a hand-authored fixture already produced one wrong test vector in this
project. If this repo is ever made public, replace the mantissas and keep the flags and lengths —
no test loses coverage.
