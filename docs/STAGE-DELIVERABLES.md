# Stage deliverables — visible progress that compounds

Every stage ends with something you can **look at**, not a green checkmark in a terminal.

The organizing idea: **each stage's deliverable is a panel of the admin console.** They are not demo
pages that get thrown away — each one is the real monitoring surface for the thing that stage built,
and by the end of Stage 3 the admin Overview screen exists, assembled entirely from panels that each
had to genuinely work before they could be drawn.

That gives progress two properties worth having. It is visible — the page fills in. And it is
honest — a panel can only render if the subsystem behind it actually reports.

```
Stage 0 ──▶ Host panel        ─┐
Stage 1 ──▶ Radios panel      ─┤
Stage 2 ──▶ Recovery panel    ─┼──▶ admin Overview screen
Stage 3 ──▶ Ingest panel      ─┘
Stage 4 ──▶ + all four radios live
Stage 5 ──▶ + Alarm panel  ──▶ the console is complete
```

All panels obey the design constraint from `PROMPT-admin.md`: **unknown never looks like healthy**,
and no status renders without the age of the observation behind it.

## Stage 0 — Hardware floor

**Deliverable:** `artifacts/system-report.html` — a generated hardware inventory you open in a
browser.

Every row is a fact read from the running box, with the command that produced it shown inline so the
page is auditable rather than asserted:

| | Reads |
|---|---|
| Root filesystem | `/dev/nvme0n1p1` · NVMe · *N* GB free |
| microSD | `/boot/firmware` only |
| Bluetooth | 1 adapter · `hci0` · Bus USB · UP RUNNING |
| Audio | USB DAC card *N* · non-HDMI sink present |
| Watchdog | `/dev/watchdog` present · `RuntimeWatchdogSec=15` |
| Governor | `performance` · 2.4 GHz |
| Thermal | *N* °C · `throttled=0x0` |
| Network | 5 GHz · ch *N* · *N* dBm |

Generated by `scripts/system-report.sh`, which is also the **Stage 0 acceptance check** — it exits
nonzero if any row is in a failing state. One script, two jobs: the report you look at and the gate
that passes.

**Why it's worth building:** the Group A tasks each verify one fact in isolation. This is the first
time you see the whole box in one view, and it is the thing you re-run after any hardware change
forever after.

→ becomes the admin console's **Host** panel.

## Stage 1 — Thesis spike

**Deliverable:** `artifacts/night1.html` — the eight-hour Polar H10 capture, rendered.

Not a number in a log. An actual page with:

- **A connection timeline** — one horizontal bar across 8 hours, solid where connected, broken where
  not. You see the night at a glance.
- **A gap histogram** — counts in `<2s · 2–10s · 10–60s · 60s–5m · >5m` buckets.
- **The headline numbers** — total duration, RR intervals captured, longest gap, drops.
- **An RR-interval trace** for the whole night, with gaps drawn as gaps.

**This is the most important artifact in the project.** Everything rests on the Pi holding a BLE
connection all night, and this is the page that tells you whether it does. Keep every night's report;
comparing night 1 against night 30 is how you find slow degradation.

**Acceptance is already in the plan:** `gap_histogram.py --require-duration-hours 8
--max-gap-seconds 300` exits nonzero if the night was too short or a gap too long. The HTML is the
same data, made legible.

→ becomes the admin console's **Radios** panel (reconnect history, per-source liveness).

## Stage 2 — Storage floor

**Deliverable:** `artifacts/recovery.html` — the answer to *"what would I lose if this died right
now?"*, stated as a duration and a row count.

- Last full backup, last incremental, WAL archive lag
- **Last verified restore** — timestamp, duration, tables compared, row-count diff, pass/fail
- Repository size and retention window
- Postgres size, growth rate, projected time to fill the disk

The restore-verification row is the point. A backup that has never been restored is a hypothesis, and
this panel is where the hypothesis becomes a measurement — or visibly doesn't, because the design
rule says a verification that hasn't run recently degrades to **unknown**, never to OK.

Fed by `/var/lib/vitals/restore-verify.json`, which `verify-restore.sh` already writes.

→ becomes the admin console's **Recovery** screen.

## Stage 3 — vitals core

**Deliverable:** `artifacts/first-sample.html` — one blood pressure reading, traced end to end.

The whole path made visible for a single real measurement:

```
A&D UA-651BLE  ──BLE indication 0x2A35──▶  bp_collector
   raw bytes: 06 76 00 4A 00 59 00 …
        │ SFLOAT decode (IEEE-11073, not IEEE-754)
        ▼
   systolic 118 mmHg · diastolic 74 · MAP 89 · pulse 62
        │ vitals_append → range check against registry
        ▼
   spool   (COPY-binary row: source=6, type=6, session_id, seq, ts, 118.0)
        │ vitals-spool-drain
        ▼
   PostgreSQL  samples · 1 row
```

Plus the registry entry that governed it (canonical unit, valid range) and the provenance stamp with node
id. Every hop shown, so when something is wrong later you know what a *correct* trace looks like.

**Why this one matters:** it is the first proof that the narrow waist works — that a real
measurement from real hardware lands in the system of record with correct provenance and correct
units. Everything after Stage 3 is more sources through the same path.

→ becomes the admin console's **Ingest** panel.

## Stage 4 — BLE fleet

**Deliverable:** the admin **Overview** screen, live, with all four sources reporting.

The four panels from Stages 0–3 assembled into one page, now driven by `vitalsd`'s health endpoint
instead of static generation. This is the first time the console is a real thing rather than a set of
artifacts.

Acceptance: leave it open for one night. Every source's liveness must track reality — including
degrading to **unknown** when a sensor drops, never sitting on a stale OK.

---

## Stage 5 — Detector and klaxon

**Deliverable:** two things, and the project's actual goal.

**`artifacts/replay-report.html`** — a historical night replayed through `cns-engine`, showing the
tier state machine's path over time against the signals that drove it, with every threshold crossing
marked. This is what makes threshold tuning empirical: change a constant, replay six months, count
what would have fired.

**The alarm itself.** With the iPhone powered off and the house internet disconnected, a replayed
desaturation drives the tier machine to `klaxon` and the speaker sounds. Nothing else in this
project matters if this does not happen.

→ adds the admin console's **Alarm** panel: self-test history, audio device state, and time since
last proven-working. A klaxon that cannot sound is the failure mode that matters, and it is invisible
unless it is on the glass.

## Rules for every deliverable

1. **Self-contained HTML.** No build step, no CDN, no server. Open it in a browser on any machine,
   or attach it to an email to a doctor.
2. **Generated by the same script that gates the stage.** The artifact you look at and the check
   that passes are one thing, so the picture can never drift from the truth.
3. **Committed to `artifacts/`** with a date. They accumulate into a record — night 1 versus night
   30 is how slow degradation gets caught.
4. **Unknown never looks like healthy.** Every status carries the age of the observation behind it,
   and degrades to unknown when that age exceeds the expected interval.
5. **It must survive being looked at in six months.** Enough context on the page that you don't need
   this repo open to read it.
