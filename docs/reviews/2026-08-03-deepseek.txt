 3. Where is the design wrong, not just incomplete?

 Let me interrogate the specific candidates:

 - HLC justification: The design says "An HLC exists to merge writes from multiple
   independent nodes without a coordinator." But who actually writes concurrently
   to the same (source, type, timestamp) key? The Pi is the single writer for
   Polar, EMAY, BP. The phone pushes HealthKit data. A watch might arrive later.
   But different sources write different source values, so they never conflict on
   the primary key (source, type, timestamp). The only conflict scenario is if two
   nodes write the same (source, type, timestamp) — but source is per-device, so
   this can't happen unless two devices claim to be the same source. The HLC adds
   complexity (3 columns, a merge algorithm, a node_id file that must never be
   regenerated) for a problem that doesn't exist. The total order argument ("the
   one HealthKit never had") is weak — you can get total order from a simple
   sequence number per source plus the source's own timestamp. The HLC feels like
   elegant engineering for a non-problem.

 - COPY-binary spool vs alternatives: The spool design is genuinely clever but has
   real problems. (1) The format is not portable across Postgres major versions,
   so upgrades require draining the spool — the upgrade runbook must remember
   this. (2) The format is architecture-dependent (network byte order but the data
   is still architecture-tied). (3) If a schema change to samples happens while
   there's data in the spool, the drainer must refuse to drain (the --verify

   no check for this. (4) The spool is a binary format that can't be inspected
   with standard tools. If something goes wrong, debugging requires a custom tool.

   ordering? (2) If a registry change adds a new type that a new sqitch

 1. What is missing that will hurt?

 Ranked by severity:

 ### 1a. Disk-full behavior is entirely unspecified

 The draft is detailed about the happy path — spool rotates at 64 MB or hourly,
 drainer streams into Postgres, offset advances. Zero words on what happens when
 the NVMe fills. A one-night Polar H10 capture at RR-interval granularity is ~250
 MB. If the drainer is down for four nights, the spool reaches ~1 GB. If Postgres
 samples table grows (uncompressed) for months, the database itself fills the
 disk. There is no df check, no ENOSPC handler, no alarm, no backpressure on
 collectors. When it fills — and it will, because the retention policy only ages
 out at 2 years and the compression policy lags 7 days — the first thing that
 fails is random: a collector write(), a Postgres COMMIT, pgBackRest's archive.
 What breaks: the system fails nondeterministically at the worst possible moment
 (mid-night, mid-backup). Fix: disk watermark checks in the health endpoint; a
 dedicated vitals-disk-watch timer that fires an alert at 80% and refuses new
 spool segments (not new samples — spool segments) at 95%.

 ### 1b. ALSA write acceptance ≠ sound produced

 The klaxond self-test (§5.1) "confirms via ALSA that the device accepted the
 write and the expected sample count was consumed." This tests the software stack.
 It does not test that the amp has power, the speaker cone hasn't torn, or the USB
 DAC hasn't silently reset to a different output. A USB DAC that disappears and
 reappears gets a new card number; the /etc/asound.conf from T-A2 points to a card
 number N that may now be wrong. ALSA will still accept writes — to the wrong
 device. What breaks: klaxond self-test passes nightly while the physical speaker
 is dead. Fix: the self-test must include a loopback path (mic near speaker
 confirming SPL) or at minimum read back the DAC's hardware mixer state and
 compare against the expected card identifier (USB VID/PID, not card number).

 ### 1c. No spool segment ordering or partial-drain discipline

 Amendment §2.1 lists seg-<epoch>.copybin as "rotated segments awaiting drain" but
 never specifies: (a) the drain order across segments (must be chronological), (b)
 what happens when a new segment is rotated while the drainer is mid-drain on an
 old one, (c) how the drainer resumes after crash when cur.offset is mid-segment
 but a rotated segment also exists (does cur.offset apply to the active segment
 only or to a global position?), (d) the exact mechanism by which a fully-drained
 segment is deleted. These are all implementable, but the spec undersells the
 complexity. A drained segment that isn't deleted gets replayed on restart (safe,
 ON CONFLICT handles it), but the offset file semantics are underspecified enough
 that a wrong implementation could skip segments.

 ### 1d. The drainer's cur.offset is a single file — what does it mean across
 segment rotations?

 If cur.offset tracks the byte offset within cur.copybin, and that file is rotated
 at 64 MB, the offset resets to 0 on rotation. But the drainer might be mid-drain
 on the old segment when rotation happens. The drained offset for the old segment
 is somewhere in seg-<epoch>.copybin, not in cur.copybin. There needs to be either
 a per-segment offset file or a global offset. The spec says "the byte offset
 advances only after that transaction commits, and it is fsynced before the
 segment is unlinked" — but which byte offset? The drainer needs to know where it
 was in each segment. This is a spec gap that will produce an incorrect
 implementation.

 ### 1e. No observability layer at all

 The design has a health endpoint returning JSON. That is the entirety of the
 observability story. There is no structured logging, no metrics (counters for
 samples ingested/drained/rejected, histograms for drain latency, gauges for spool
 size), no alerting rules, no way to answer "is the system degrading?" without a
 human reading health JSON. The design is for a system that operates unattended
 through the night. What breaks: slow degradations — a BLE connection taking 4
 seconds to reconnect when it used to take 1, a drain batch that now takes 30
 seconds instead of 5 — are invisible until they become failures. Fix: adopt
 tracing with journald output and Prometheus metrics exposed from vitalsd. The
 health endpoint is a snapshot; metrics are a history.

 ### 1f. The generated registry.rs does not exist yet; the codegen TOML does not
 exist yet

 The Rust workspace crate vitals-registry is a skeleton: #![no_std] with no code.
 The TOML file at vitals/registry.toml does not exist. The T-D1 task still
 describes emitting vitals_types.h (a C header) and makes no mention of generating
 generated.rs. This is acknowledged as "follow-up on the T-D1 branch" but the
 tasks haven't been reworked. Since T-D2 (SFLOAT decoder) is done and the decoder
 references types by integer ID, this isn't blocking — but every subsequent task
 that needs source/type constants will be blocked until the generator emits Rust.
 The C/Rust language decision document won; the tasks lost.

 ### 1g. The samples_hypertable migration uses migrate_data => TRUE but runs
 immediately after samples table creation

 This is currently harmless — the table is empty. But the migration is
 unrepeatable: if someone runs sqitch rebase after data exists, migrate_data =>
 TRUE on a large samples table will lock it for the duration of a full table scan
 + rewrite. On a Pi 5 with 8 GB RAM and a 1 TB NVMe, this could take hours and
 block all ingest. Fix: either use migrate_data => FALSE (the table is empty at
 deploy time, so nothing to migrate), or document the "must be empty" precondition
 in the sqitch plan.

 ### 1h. The cns-engine data path is undefined

 The design says cns-engine subscribes to vitalsd and holds ~60s ring buffers. But
 how does it subscribe? Through the vitals_subscribe() API? What selectors? Does
 it get every sample or only the types it cares about? The subscribe API is
 specified (unfiltered fan-out per selector), but the connection between vitalsd →
 cns-engine → klaxond is a box in the diagram with no wire protocol. Tasks D4
 specifies subscribe but doesn't specify how cns-engine uses it. This is Stage 5,
 so not in the current change scope, but the API that cns-engine depends on is
 being built now.

 ### 1i. Node ID resilience is underspecified

 hlc.c reads /var/lib/vitals/node_id "generated on first run from getrandom(2),
 never regenerated." If that file is lost (filesystem corruption, accidental
 deletion, migration to new hardware), the node effectively becomes a new writer.
 HLC-merge semantics handle this — different node_id means different clock lineage
 — but all existing data stamped with the old node_id has a different "clock."
 This isn't necessarily wrong (the HLC design handles multiple writers), but the
 implication that a node identity loss is silent and unrecoverable should be
 explicit. A node that regenerates its ID silently looks like a different node
 that happened to write the same source values — the HLC comparison between old
 and new stamps still works but you've lost the "this is the same physical Pi"
 property.

 2. What tool, library, protocol, or platform feature should this be using and
 isn't?

 sd_notify / libsystemd for EVERY daemon, not just vitalsd. vitalsd.service has
 Type=notify and WatchdogSec=30. vitals-spool-drain.service isn't even defined yet
 and needs both. Every collector service needs at minimum WatchdogSec= with a
 main-loop ping so a wedged BLE stack reboots the collector. The Rust sd-notify
 crate is already identified. Cost: trivial — one sd_notify::notify(false,
 &[sd_notify::NotifyState::Watchdog]) call per main-loop iteration.

 tracing + tracing-subscriber with journald. The design has no logging story.
 tracing is the Rust ecosystem standard for structured, async-aware logging and
 integrates with journald via tracing-journald. This replaces: fprintf(stderr,
 ...) (which is what a C daemon would do, and what the Rust port will inherit by
 default). Cost: two crate dependencies, a few lines of subscriber setup in each
 binary's main(). This is not optional — a life-safety daemon that runs unattended
 must leave evidence of everything it decided.

 metrics crate + Prometheus exporter. The health endpoint returns a JSON snapshot.
 A snapshot cannot tell you the drain rate over the last hour, or whether
 reconnect latency is trending up. The metrics crate (zero-cost when not
 recording) with a Prometheus scrape endpoint gives this for ~3 crate
 dependencies. Cost: defining ~10 metrics (samples_appended, samples_drained,
 spool_bytes, drain_batch_seconds, ble_reconnects, etc.) and one new HTTP endpoint
 on the API server. Replace: JSON health snapshot as the only quantitative view.

 btleplug should be evaluated alongside bluer. The language choice doc (§2 in
 language-choices.md) recommends bluer because it's the official BlueZ Rust
 binding. btleplug is a cross-platform BLE library with a higher-level async API,
 more active development, and the same BlueZ backend on Linux. The cross-platform
 property matters: you can develop and CI-test collector logic on macOS against a
 simulator. bluer is Linux-only and adds friction to the edit/test cycle. The
 design already calls out compile times as a Rust cost — cross-platform
 development partially offsets this. Cost: a second dependency to evaluate;
 btleplug is a larger abstraction with more moving parts.

 sqlx in addition to (or instead of) tokio-postgres for the drainer.
 tokio-postgres does binary COPY and is the right low-level choice. sqlx offers
 compile-time query checking against a live database — if the spool drain query
 references a column that was renamed, the build fails rather than the drainer
 crashing at 3am. Since the drainer runs one query pattern (COPY staging,
 INSERT...ON CONFLICT, advance cursor), this can be verified at compile time.
 Cost: one more dependency; sqlx can sit beside tokio-postgres for the few
 query-shaped operations while COPY uses the raw driver.

 serde + serde_json for the health endpoint and config. The health endpoint spec
 says "CBOR" but does not commit to a serialization library. CBOR is fine for the
 wire protocol but JSON is more debuggable for health. Either way, serde is the
 Rust serialization framework and should be named explicitly. Cost: already a
 transitive dependency of nearly everything.

 rustls (not needed). No TLS in the current design. Correct — Cloudflare Tunnel
 terminates TLS. This is the right call.

 TimescaleDB + pgBackRest + sqitch — all correct. No argument with any of these.
 TimescaleDB on a Pi 5 for single-user time-series is overprovisioned but gains
 you compression, continuous aggregates, and gapfill — all three would otherwise
 be hand-written bugs waiting to happen. pgBackRest's WAL archival and
 point-in-time recovery is the right backup story. Sqitch's verify scripts per
 migration are the right discipline. Each is the best-in-class choice for its
 role.

 Rust no_std for decoders — correct and well-executed. The vitals-decode crate
 with #![no_std], #![forbid(unsafe_code)], and exhaustive u16 domain test is the
 gold standard for this class of code.

 3. Where is the design wrong, not just incomplete?

 ### HLC is solving a problem this system does not have

 The design claims (§2.1) "An HLC exists to merge writes from multiple independent
 nodes without a coordinator. It was over-engineering for a single phone. It is
 exactly right for a Pi, a phone, and a watch that each observe reality
 independently and reconcile later."

 This is a category error. Multiple writers does not mean multiple writers to the
 same key. The primary key is (source, type, timestamp). source is per-device: the
 Polar H10 writes source=1, the phone writes source=2, the watch (if it ever
 arrives) writes source N. These are disjoint by construction — two nodes never
 contend for the same primary key. The only conflict scenario is two nodes writing
 with the same source value, which means they're impersonating each other and the
 system is already broken at a protocol level.

 What HLC actually provides here is a total order across sources — "did the Polar
 record HR 72 before or after the phone recorded sleep stage 3?" This is a real
 question, but it's answered adequately by: the Pi's monotonic clock stamps each
 append. Since vitalsd is the single writer (design §4.1: "Single writer. Stamps
 HLC."), every sample already gets stamped in order by one process. The phone
 pushes to hk-receiver which writes through vitalsd — the same single writer. The
 HLC's multi-writer merge (hlc_merge) is dead code: vitalsd never receives a
 remote HLC, because all writes go through vitalsd.

 The design conflates "multiple systems observe reality" with "multiple systems
 write to the store." The former is true. The latter is designed away — that's the
 whole point of vitalsd as the single writer. If the single-writer property holds,
 HLC degenerates to a monotonic sequence number. If it doesn't hold (e.g., the
 phone writes directly to Postgres someday), then the single-writer design has
 been violated and there are bigger problems than clock merge.

 Severity: not a correctness bug — HLC with a single writer is just a fancier
 sequence number — but it adds 3 columns, a merge algorithm, a node-id persistence
 requirement, and a WAL-tail cursor that must be an HLC position rather than a
 simple integer. That complexity has already consumed design attention that should
 have gone to the spool drainer's operational behavior. Recommendation: either (a)
 make the multi-writer scenario real by having the phone write directly rather
 than through hk-receiver/vitalsd, or (b) replace HLC with a BIGSERIAL generated
 by vitalsd. If (a), the HLC merge is load-bearing and must be tested with two
 concurrent writers. If (b), you shed an entire module.

 ### The COPY-binary spool is clever but its operational failure modes are worse
 than the problem it solves

 The spool replaces SQLite-as-ingest-buffer. The stated problem with SQLite was
 "dialect mismatch" — every row crossed a translation layer because SQLite and
 Postgres have different SQL, types, NULL semantics. This is a real concern but
 it's a developer-convenience concern, not a correctness one. A translation layer
 from SQLite C types to Postgres binary COPY fields is ~50 lines of code that
 changes rarely (only when samples schema changes, which is rare in an append-only
 table). That 50-line translation layer, written once and tested once, has the
 following advantages over the spool design:

 1. You can query the buffer during development/debugging (SELECT * FROM samples
    WHERE ...).
 2. You get SQL-level idempotency (ON CONFLICT) natively rather than through a
    staging table dance.
 3. The buffer survives schema changes — SQLite's STRICT type is weaker than
    Postgres types but the translation layer is versioned with the table schema,
    and old rows in the buffer are still readable and drainable.
 4. You don't need a separate drainer daemon — vitalsd can tail its own WAL
    (single process, one less moving part to monitor).
 5. Crash recovery: SQLite WAL is battle-tested; a custom binary spool with fsync
    discipline and dual daemon crash-recovery semantics is new code with new bugs.

 The spool's headline win — "no translation layer" — is real but it trades a
 small, testable, versioned translation for an operational surface area (drainer
 daemon, segment management, offset tracking, schema-version locking) that is
 larger, harder to test, and has already produced a spec-level bug (UNLOGGED vs
 TEMP staging table). The libpglite alternative was rejected as "WIP," but the
 spool design is also WIP — just custom WIP instead of someone else's.

 I'm not saying the spool design will fail. It can be made to work. But it is more
 complex than the problem required, and the complexity is concentrated in the part
 of the system (durability path, crash recovery, operational monitoring) where
 complexity is most expensive.

 ### The sqitch/generated split will drift silently

 Amendment §7 describes "Two owners, split explicitly": sqitch owns structure,
 generated registry.sql owns reference rows. The sqitch deploy creates vitals_type
  and vitals_source as empty tables with id INTEGER PRIMARY KEY. The generated SQL
 is supposed to INSERT ... ON CONFLICT DO UPDATE. This split has four failure
 modes:

 1. Ordering: what runs registry.sql after sqitch? Not sqitch — sqitch doesn't
    know about generated SQL. If the generated SQL is applied by vitalsd on
    startup, then a new source added to registry.toml requires a vitalsd restart,
    not just a sqitch deploy. This is never stated.

 2. Column drift: if a sqitch migration adds a column to vitals_type (e.g.,
    display_order INTEGER), the generated INSERT statements now fail because they
    don't include the new column. Conversely, if the generator changes a column
    name but sqitch hasn't, the inserts fail. There is no automated test that
    sqitch-deployed table shapes match the generator's expected shape.

 3. The generator hasn't been trimmed yet. The amendment says "The generator
    currently emits both structure and rows. It must be trimmed to rows only."
    This is marked as follow-up on T-D1. Until it's done, the generator and sqitch
    are both emitting structure — which means the current state of the codebase
    has the split on paper but not in practice.

 4. sqitch verify scripts don't check reference data. registry_tables verify only
    checks that the tables exist and have CHECK constraints. It doesn't verify
    that the expected rows are present. So if the generator fails to run, sqitch
    verify passes and no one knows the reference data is stale.

 Fix: generate registry.sql as a sqitch migration (a new one on each registry
 change with a timestamped tag) rather than as a side channel. This puts it in
 sqitch's dependency graph and makes it subject to sqitch's verify discipline. The
 "reference data is reconciled on service start" idea is fragile compared to
 "reference data is migrated like everything else."

 ### The process topology diagram implies vitalsd replays to Postgres but the
 spool design puts a separate daemon in that path

 The architecture diagram (§3) shows:

 ```
   collectors → vitalsd → cns-engine → klaxond
                   │
                   ▼ WAL-tail replication
              PostgreSQL
 ```

 With the spool amendment, the actual path is:

 ```
   collectors → vitalsd → spool.copybin
                            │
                            ▼ vitals-spool-drain
                         PostgreSQL
 ```

 vitalsd no longer touches Postgres. The drainer is a separate daemon, with its
 own systemd unit, its own crash semantics, and its own monitoring surface. The
 diagram is wrong in a way that matters: a reader of the architecture doc thinks
 vitalsd owns replication; in reality a process not shown on the diagram owns it.
 The health endpoint lives on vitalsd — but vitalsd has no visibility into drainer
 progress, spool size, or drain latency. The component that needs the most
 monitoring has no health endpoint.

 ────────────────────────────────────────────────────────────────────────────────

 4. What I would do differently at the architecture level

 Keep the architecture but fix the data path. The core insight — Postgres with
 TimescaleDB as the system of record, vitalsd as a single-writer Unix socket
 server, decoders as pure functions, the registry as generated code, the
 life-safety path outside Docker — is correct and well-reasoned. I would not
 change any of it. I would change how data gets from vitalsd to Postgres.

 Replace the COPY-binary spool + drainer daemon with the simpler thing: vitalsd
 writes directly to Postgres. The original design had it writing to SQLite and
 tailing WAL — that was the wrong indirection. But going from vitalsd → spool →
 drainer → Postgres is also an indirection, just a different one. The right
 indirection is none at all: vitalsd opens a tokio-postgres connection, writes
 samples via COPY ... FROM STDIN (FORMAT binary) in batches (every 250ms or every
 N samples), and commits. If Postgres is unreachable, buffer in memory with a
 bounded ring (up to e.g. 60 seconds of data) and drop on overflow — better to
 lose old samples than stop collecting. vitalsd is already the single writer;
 making it also the single writer to Postgres eliminates the drainer daemon, the
 spool segment management, the offset tracking, the UNLOGGED-vs-TEMP staging table
 ambiguity, the schema-version locking problem, and the monitoring gap where
 vitalsd's health endpoint can't see the drainer.

 This is one process instead of two, one place to monitor instead of two, and zero
 custom on-disk formats instead of one. The cost is that vitalsd now depends on a
 Postgres connection — but it already depended on the spool drainer maintaining
 one, so the dependency exists either way, just in a different process.

 Drop the HLC for now, add it when you have a second writer. The single-writer
 design makes HLC a sequence number. A BIGSERIAL or a monotonic counter in vitalsd
  gives the same total order with none of the infrastructure. If the phone later
 writes directly to Postgres (the scenario HLC exists for), add HLC then — it's a
 migration to add three columns, and the existing data gets stamped with the
 node's HLC at migration time. You lose nothing by deferring it, and you gain back
 design attention for the things that are currently underspecified (spool drainer
 semantics, disk-full behavior, observability).

 What I checked and found genuinely fine

 - The SFLOAT decoder (crates/vitals-decode/src/sfloat.rs). Correct handling of
   all sentinel values (NaN, NRes, ±INFINITY, Reserved — all return None). The
   0x0FFF ≠ 0x07FF distinction is right. The libm_powi10 lookup table is a smart
   no_std solution. The exhaustive for raw in 0u16..=u16::MAX test over the entire
   16-bit domain is stronger than any fuzzer — it proves every input produces
   either Some(finite) or None. The crate attributes (#![no_std],
   #![forbid(unsafe_code)], panic = "deny", indexing_slicing = "deny") enforce
   exactly the right invariants at compile time. No notes.

 - The workspace-level lints (Cargo.toml). cast_possible_truncation = "deny",
   cast_precision_loss = "deny", cast_sign_loss = "deny" — these are exactly the
   right lints for medical data processing. unsafe_code = "forbid" at workspace
   level. panic = "abort" in release. This is the strictest reasonable Rust
   configuration and it matches the C build's -Wall -Wextra -Werror -Wshadow
   -Wconversion discipline.

 - The sqitch verify scripts. The 1 / count(*) trick to turn "zero rows" into a
   division-by-zero error is idiomatic and correct. The samples_hypertable
   revert's refusal to destroy data (RAISE EXCEPTION 'refusing to revert
   samples_hypertable: samples has rows') is exactly right. The extensions
   revert's refusal to drop timescaledb is similarly correct.

 - The retention dependency ordering. retention depends on samples_1min in the
   sqitch plan, and the verify script checks that the continuous aggregate exists
   before allowing retention to proceed. This prevents the exact failure mode the
   design calls out: dropping raw data before the rollup exists.

 - The append-only + ON CONFLICT DO NOTHING design. This is the simplest possible
   idempotency mechanism and it's correct. Combined with the cursor discipline
   (offset advances only in the transaction that wrote the rows), it makes the
   drainer crash-safe without distributed transactions.

 - The TimescaleDB time_bucket_gapfill enforcement of "unknown ≠ OK." Using the
   database's native gap-fill to return explicit NULL rows rather than silently
   absent buckets makes the invariant structural rather than conventional. The ban
   on locf() and interpolate() for physiological series is correctly reasoned —
   gap-filling a missing SpO₂ is lying.

 - The WITH NO DATA on the continuous aggregate. Prevents a full table scan at
   creation time. Correct.

 - The performace governor and watchdog being armed before any daemon runs. Stage
   0 gets the hardware right before software depends on it. This ordering
   discipline is the right instinct and it's applied consistently.
